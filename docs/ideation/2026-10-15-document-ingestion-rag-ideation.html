Ideation: Document upload, ingestion and RAG / GraphRAG readiness

Which directions are worth exploring for letting people upload files, ingesting them through a pipeline, and making the result retrievable by vector RAG and GraphRAG, without weakening the governance promises Lattice already keeps.

Grounding Context

Codebase Context
  • Content is one immutable row per version. DocumentVersion holds title and body as text, plus a generated, weighted search_vector tsvector with a GIN index (backend/app/models.py:148-176). A trigger rejects every UPDATE and DELETE (KTD4). MAX_BODY = 200_000 characters and validate() are the only content gate (services/documents.py:17-29).
  • There is no file concept. POST /api/documents takes JSON title + body (routers/documents.py:46-53). It runs validate() before authorize(). There is no multipart route, parser, MIME check, processing status or chunk table. No embedding client is in pyproject.toml.
  • Lifecycle via pointers. Document.serving_version_id, pending_version_id and withdrawn_at drive the lifecycle. Approval is one conditional pointer flip that raises STALE_DRAFT (services/documents.py:103-125). withdraw() touches nothing derived, because today the only derivative is a generated column in the same row.
  • Retrieval is one SQL statement. read_clause(subject, RETRIEVE, d, v) runs in the WHERE before ORDER BY ts_rank … LIMIT (services/search.py:24-31). README:55 says: “Search cannot fetch the ten best matches and then drop the ones you may not read.” Policy is one module (policy.py), proved against an independent reference model by a Hypothesis state machine (tests/test_policy_properties.py).
  • Closed MCP surface. DECLARED = {"search_knowledge", "get_evidence"} is guard-tested (mcp_server.py:42). Audit stores returned version ids only (mcp_server.py:173-175). Audit writes are in-transaction and fail closed.
  • Infrastructure. compose.yaml runs only db (stock postgres:18, no pgvector), migrate and app. There is no worker, queue or scheduler. Tests use testcontainers Postgres 18, and a guard fails any new route without grounded coverage.
  • Product boundary. PRODUCT.md:50 says: “Not built, do not show or imply: vector or hybrid retrieval, file ingestion, citations …”. Shipping any of this changes PRODUCT.md and README's deferred table (README.md:87).

Additional context

governed-knowledge-store-thoughts.md is the original proposal: approved knowledge served to agents over MCP with permissions, citations, audit and withdrawal; FastAPI + Postgres/pgvector + LlamaIndex. It scopes v1 file types to Markdown and text-PDF (~line 66), leaves the embedding provider undecided (~110), and treats “a bounded knowledge graph” as a stretch goal (lines 112-124).

Past learnings

None. The repo has no docs/solutions/ store yet.

External context

  • pgvector applies WHERE after the approximate HNSW scan, so a selective ACL returns too few rows. v0.8 iterative scans trade latency for recall. (pgvector docs)
  • Glean treats ACLs as both an index-time and a query-time concern, and warns that “allow all for now” forces a reindex later. (Glean permissions SDK)
  • Microsoft GraphRAG keeps text_unit_ids lineage, but its entity descriptions and community reports are LLM-written prose. LightRAG supports incremental insert and delete. Graphiti stores temporal facts with provenance. Apache AGE runs Cypher inside Postgres. (GraphRAG outputs, Apache AGE)
  • Parsers convert broadly and guarantee nothing. LlamaParse continues past OCR errors with empty text by default. Unstructured extracts PDF tables only in hi_res mode. Docling has documented OOM and garbled-font failures. (Docling troubleshooting, Unstructured tables)
  • Anthropic's contextual retrieval adds 50-100 generated tokens of context to each chunk before embedding and BM25. Parent-child retrieval searches small spans and returns a coherent parent. (Contextual Retrieval)
  • The OWASP RAG cheat sheet calls for cascading deletion to chunks, embeddings, indexes and caches, with orphan scans and deletion logs. It also warns about indirect prompt injection through hidden text. The OWASP File Upload cheat sheet calls for allowlists, signature checks, size and decompression limits, and isolated processing. (RAG Security, File Upload)
  • Ragas evaluates retrieval and answers. It does not measure parse fidelity or citation correctness. (Ragas)

Topic Axes

Ranked Ideas

The thread through the set

Most ideas share one rule. Every derived artifact (chunk, vector, edge, report) is a row keyed to an immutable version and readable only through the existing read_clause. Ingestion then extends Lattice's governance instead of sitting beside it. Ideas 3, 5 and 6 are three faces of that rule.

  2. I2. Fail-closed extraction receipt
  3. I3. Chunks are spans of the approved body

  5. I5. One derivations ledger: readiness, pipeline version, withdrawal

I1Upload & intakeConfidence 85%Complexity Medium

I1. Upload is a narrow waist into the existing draft path

Description

Each file type is an adapter whose only output is (title, body). That output enters through the existing validate() → new_draft() path, so an uploaded PDF becomes an ordinary unshared draft in the Approvals queue, reviewed with the existing diff. The original bytes are stored once, content-addressed by sha256. They sit on an intake record with the detected type (by file signature, not MIME), parser id and version, and an outcome: drafted, or rejected with a reason. They are an attachment of the version, never the retrieval unit. Authorization moves before parsing. Re-uploading a file with the same hash is a no-op, and a matching title offers “add as a new version” rather than creating a duplicate document.

Basis

  • direct: title, text = svc.validate(body.title, body.body) then await authorize(...) then new_draft(...) (routers/documents.py:47-52). This is the one version-creation path, and its validate-then-authorize order is wrong once a parser sits in front.
  • direct: “Every agent-visible field lives on the version, so nothing reaches retrieval unreviewed” (plan KTD4, line 287). DocumentVersion has no source or provenance fields (models.py:151-157).
  • direct: the seed's pending edit pattern, “v1 keeps serving until v2 is approved” (seed.py:177-186), is what re-uploads should reuse.
  • external: the OWASP File Upload cheat sheet: allowlist, signature checks, generated names, size and decompression limits, isolated processing.

Rationale

Each new format costs one adapter, not a second lifecycle. Approval, unshared-by-default, audit, withdrawal and the review UI apply to files without new code. Keeping the source hash and parser version on the version makes “approval binds to one exact immutable version” cover what was read from which file, and lets a better parser later re-extract from the sealed original.

Downsides

The 200k-character cap rejects roughly 60+ page PDFs, so the cap becomes a deliberate product decision. A synchronous parse inside the request is fine for Markdown and text-PDF but not for large or OCR'd files, which pushes toward I5's job table. Re-extraction drafts need a system actor, since created_by is a non-null user FK, and a rule for not clobbering a human's pending draft. Zip and folder intake was left out deliberately because it adds decompression-bomb surface.

I2Extraction fidelity & reviewConfidence 80%Complexity Medium

I2. Fail-closed extraction receipt

Description

Every parse writes a receipt keyed to the draft. It records the parser and its config, per-page character counts, and flags for empty or failed-OCR pages, dropped tables, skipped images, and hidden-layer content (white-on-white or off-page text, comments, tracked changes, hidden sheets, alt text). Hidden-layer content is excluded from the body by default and shown in a labelled section of the review card. Any flag disables Approve until the approver acknowledges that flag, and the acknowledgement is stored with the decision. “Parsed with problems” becomes a visible state, not a green tick. As an option for scanned or untrusted sources, a second independent reading (rendered-page OCR against the text layer) can point the reviewer at the spans where the two readings disagree.

Basis

  • direct: escape_invisible escapes only unicodedata.category(c) == "Cf" (services/documents.py:150-153). The plan admits that characters which “render invisibly even in raw text … can still pass review, a known v1 limitation” (plan line 260).
  • direct: mcp_server.py's DATA_NOTE tells agents “Every item was approved by a workspace admin or owner.”
  • external: LlamaParse continues after OCR errors with empty text unless told to fail. Unstructured extracts tables only in hi_res. Docling can garble fonts. OWASP lists hidden-text prompt injection.

Rationale

Today the human typed the body the reviewer reads. Once a parser sits between file and body, the reviewer approves the parser's output without seeing what it dropped or what the file was hiding. The review_diff shows what text was produced, but never what is missing, which is the dominant parser failure. This is the point where “approved by an admin” either stays true or quietly becomes false.

Downsides

Hidden-layer and per-page confidence signals depend on parser APIs that have not been verified, and they vary by parser. VersionDecision.reason is optional and capped at 500 characters, so a mandatory acknowledgement needs a schema or service change. The dual-reading option adds native OCR dependencies to a slim image, and its divergence output may be noisy (columns, ligatures), so it stays optional.

I3Permission-safe retrievalConfidence 85%Complexity Medium

I3. Chunks are spans of the approved body; citations become checkable

Description

A chunk stores no text of its own. It is (version_id, start, end, sha256) into the immutable approved body, plus its embedding. A derivation-time assert fails the run if any chunk does not equal body[start:end]. search_knowledge returns span references, get_evidence accepts a span and returns exactly that passage, and the audit row records spans, not just versions. Contextual-retrieval prefixes and summaries may be embedded and indexed, but they are stored separately and never returned as evidence. A citation an agent quotes back can be re-sliced and compared character for character. It can also report “that version has since been withdrawn”.

Basis

  • direct: “Immutable: a trigger rejects every UPDATE and DELETE (KTD4).” (models.py:149). Offsets into an immutable body can never go stale.
  • direct: audit records returned_version_ids=returned_ids(results) (mcp_server.py:173-175), at version granularity only. README:73 promises that “the audit trail records what each agent received”.
  • direct: citations are listed as “Not built” (PRODUCT.md:50). The proposal wants “exact supporting passages” (governed-knowledge-store-thoughts.md:68).
  • external: Anthropic contextual retrieval and parent-child retrieval show context helps ranking. Keeping that context separate from the returned span stops LLM annotations and parser side-text from reaching agents as “approved” evidence.

Rationale

Immutability makes this citation guarantee unusually cheap and strong. The span is also the shared key that chunks, graph edges (I6), withdrawal purge (I5) and the benchmark (I7) all reuse, so this one decision makes the rest of the set simpler. It extends KTD4 (“nothing reaches retrieval unreviewed”) from documents to passages.

Downsides

A new parameter on get_evidence or search_knowledge changes the guard-tested DECLARED set (mcp_server.py:42) and the endpoint matrix. Offset spans need a canonical body encoding (normalise on ingest, count in code points) or they break subtly. “Nobody else can claim this” overstates it, since offset citations exist elsewhere. What is distinctive is pairing them with exact-version approval.

I4Permission-safe retrievalConfidence 75%Complexity High

I4. Policy-first vector retrieval, born under the property test

Description

Vector search keeps the exact read_clause predicate as the security boundary, applied before ranking, the same shape as today's full-text search. Start with exact distance over the permitted set, which has perfect recall and no leak. Add HNSW only once that is measured to be too slow, and then use iterative scans with an ANN-vs-exact recall canary on the permitted corpus. Hybrid (full-text + vector) fuses inside the same filtered statement. The merge gate: the reference model gains retrievable_spans, the Hypothesis state machine asserts that vector and hybrid results equal it for every person after every step, AE10 is restated for vectors, and a deliberately leaky join is shown to fail the property.

Basis

  • direct: .where(read_clause(subject, Action.RETRIEVE, d, v), …).order_by(rank.desc(), v.c.id).limit(limit) (services/search.py:24-31). README:55 says: “a restricted-heavy corpus would return two results instead of ten, and the gaps would hint at what is hidden.” AE10 is at plan line 226.
  • direct: the property test “checks that, for every person in every workspace, the reference model, the SQL read predicates, the single-item decision, UI search and the MCP search service all agree” (tests/test_policy_properties.py:1-8). endpoint_grounds.py:1-4 keeps its oracle independent of app.policy.
  • external: pgvector filters after the approximate HNSW scan, and v0.8 iterative scans are the mitigation (verified accurate by the critique pass).

Rationale

“Permission-safe vector search” is where most RAG systems quietly leak or lose recall, and Lattice already has the oracle that makes it provable rather than arguable. Wiring every new retrieval path (vector, hybrid, graph, reranked) into the existing property test means no future strategy can ship with a leak. That is the moat the existing work already paid for.

Downsides

It needs a pgvector-enabled image in compose.yaml, the Dockerfile and the testcontainers harness. “Exact scan is fast enough” is unmeasured: managers read the whole workspace (IS_MANAGER is true()), so their permitted set is the full corpus. The embedding provider decision is still open and lands on this idea first.

I5Derived-index lifecycleConfidence 65%Complexity Medium

I5. One derivations ledger: readiness, pipeline version, withdrawal

Description

A single derivations(version_id, kind, producer, config_hash, status, error) table is at once the job queue (claimed with FOR UPDATE SKIP LOCKED by an in-process loop, so no new service), the per-version freshness view, and the purge ledger. Versions are immutable, so derived rows are only ever inserted or purged. Retrieval security never depends on the queue, because every derived table joins through read_clause and withdrawal hides content instantly. A bill of derivatives makes each derived table register a withdrawal rule. A guard test fails any new derived table without one, and a canary withdrawal proves nothing derived stays retrievable. Purge completion is written to the audit trail. config_hash lets a new embedding model build alongside the old one before a switch. The ledger also forces the one fork that has to be decided up front: when derivation runs.

Basis

  • direct: compose.yaml defines only db, migrate and app. No worker or queue exists anywhere in backend/app.
  • direct: search_vector is Computed(…, persisted=True) (models.py:159-165), so today's index is atomic with approval. Embeddings cannot be, which is exactly why the fork appears. withdraw() (services/documents.py:139-147) touches nothing derived.
  • direct: audit_events allows channel='system' with a nullable actor (models.py:276,288), so purge receipts fit the existing trail.
  • external: OWASP RAG cascade deletion, orphan scans and deletion logs; FDA-style mock recalls, where untested recall paths fail the first time they are needed; materialized-view dependency invalidation.

Rationale

It is the one piece of infrastructure every producer (parse, chunk, embed, extract) needs, and it adds no dependency beyond the Postgres already running. It splits two concerns that RAG systems usually blur: access is gated instantly by SQL, and storage is purged eventually with a receipt. That keeps “withdrawn means agents never see it again” honest the day someone adds a chunk_embeddings table.

Downsides

“Purged” is partial by design. Withdrawn bodies stay in document_versions forever under the immutability trigger, so the receipt covers derivatives only and must say so. audit.record() needs a non-person path. Option (b) sends draft text to a provider, which conflicts with (c) unless the model is local. The fork is a product decision, not an engineering one.

I6Graph knowledgeConfidence 60%Complexity Medium

I6. Governed graph: edges inherit evidence readability, deterministic first

Description

The graph has no permission model of its own. An edge is (subject_entity, predicate, object_entity) plus a set of evidence spans (I3). A person sees an edge only through the evidence they can read under read_clause. Its rendered description, degree and “mentioned in N documents” are computed from that readable evidence alone, never from a stored merged summary. Start without an LLM. An admin-approved registry of entities and aliases (payments-gateway, checkout), maintained through the same draft → approve flow, produces deterministic mention edges and “mentioned by” backlinks. This becomes the baseline any LLM extractor or community report has to beat.

Basis

  • direct: the proposal says “Every relationship should link to supporting passages and respect their permissions.” (governed-knowledge-store-thoughts.md:120) and “Apply permissions to supporting passages, graph relationships and any derived summaries.” (:81).
  • direct: in seed.py:163-175, architecture is shared to Platform and Payments, the timeouts runbook to Platform only, and the incident to Payments only. All three name payments-gateway in prose (seed.py:33-55), and no code links them.
  • direct: the proposal calls a small graph “graph-assisted retrieval” and warns that full GraphRAG “would considerably expand the first release” (:124).
  • external: Microsoft GraphRAG keeps lineage, but its descriptions and reports are LLM prose that blends sources, the one leak a row filter cannot unpick. Library authority records are the precedent for a curated alias registry.

Rationale

It turns “governed GraphRAG” from a slogan into a testable property that plugs into I4's oracle (visible_edges in the reference model). Starting deterministic makes graph-assisted retrieval buildable in days with no hallucinated edges, and answers “does a graph help here at all?” before anyone pays for LLM indexing.

Downsides

One rule is still open: an edge visible if any supporting evidence is readable, or only if all of it is. “All” over-hides co-mentions, and “any” is safe only if descriptions are never stored merged. Documents have no type field, so “incident affects service” is only co-mention until types exist. The alias registry is itself content and needs read rules or it leaks entity names. An approver-side “edge delta” view is a natural follow-on but needs this layer first.

I7Extraction fidelity & reviewConfidence 65%Complexity Medium

I7. Fidelity-and-permission benchmark on the Acme seed

Description

Turn the existing Acme Engineering scenario into a benchmark that every producer change has to pass. It contains a hostile file set (zero-width and white-on-white text, a scanned page, a table-heavy PDF) with gold spans, and questions asked as Mei, Sam, an owner and an outsider, across a withdrawn runbook, a pending edit and a rejected draft. It reports extraction completeness, allowed-only Recall@k, denied-retrieval rate (must be exactly 0), citation resolution (I3), deletion propagation (I5), and edge precision against I6's deterministic baseline. Swapping a parser, chunker, embedding model or reranker becomes a measured change.

Basis

  • direct: endpoint_grounds.py's expected visibility is “written out … not derived from app.policy, so it stays an independent oracle” (lines 1-4, 368-374). That is the same discipline, extended to retrieval quality.
  • direct: PRODUCT.md:38 already defines the negative cases: “a runbook edit awaiting approval, a withdrawn runbook, a draft and a rejected draft”. The proposal itself asks for evaluation first (governed-knowledge-store-thoughts.md:126-139).
  • external: Ragas measures retrieval and answers but not parse fidelity or citation correctness. The two planes have to be built together.

Rationale

Every choice in this slice (parser, chunk size, embedding model, contextual annotations, graph extractor) is a swappable bet. One yardstick turns each swap into evidence instead of debate. It also produces the “evidence showing how well it works” the proposal promises. The denied-retrieval number is the one most RAG vendors cannot publish.

Downsides

Building the hostile file set and gold spans is real work. A roughly six-document seed corpus is too small for meaningful recall or baseline-vs-LLM comparisons, so the corpus has to grow. Building it before any pipeline exists delays the first visible feature.
